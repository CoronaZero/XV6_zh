# 现实世界

> 来源：book-rev7.pdf，第 67–81 页（中文翻译）

真实操作系统中的缓冲区缓存比 xv6 的复杂得多，但它服务于同样的两个目的：缓存和同步对磁盘的访问。xv6 的缓冲区缓存与 V6 的一样，使用简单的最近最少使用（LRU）淘汰策略；还可以实现许多更复杂的策略，每种都对某些工作负载好，对其他不好。更高效的 LRU 缓存会消除链表，改用哈希表进行查找，用堆进行 LRU 淘汰。现代缓冲区缓存通常与虚拟内存系统集成，以支持内存映射文件。

xv6 的日志系统非常低效。它不允许系统调用并发执行更新操作，即使系统调用操作文件系统的完全不同部分。它记录整个块，即使块中只有几个字节发生变化。它执行同步日志写入，一次一个块，每个块可能都需要整整一个磁盘旋转周期。真正的日志系统解决了所有这些问题。

日志不是提供崩溃恢复的唯一方法。早期文件系统在重启期间使用清理程序（例如 UNIX fsck 程序）检查每个文件和目录以及块与 inode 空闲链表，查找并解决不一致。清理大型文件系统可能需要数小时，而且在某些情况下无法猜测不一致的正确解决方案。从日志恢复要快得多且正确。

xv6 使用与早期 UNIX 相同的基本磁盘 inode 和目录布局；这个方案多年来非常持久。BSD 的 UFS/FFS 和 Linux 的 ext2/ext3 使用基本相同的数据结构。文件系统布局中最低效的部分是目录，每次查找都需要对所有磁盘块进行线性扫描。当目录只有几个磁盘块时，这很合理，但对于保存许多文件的目录来说代价高昂。Microsoft Windows 的 NTFS、Mac OS X 的 HFS 和 Solaris 的 ZFS 等文件系统将目录实现为磁盘上的块平衡树。这很复杂，但保证了对数时间目录查找。

xv6 对磁盘故障的处理很简单：如果磁盘操作失败，xv6 会 panic。这是否合理取决于硬件：如果操作系统位于使用冗余来掩盖磁盘故障的特殊硬件之上，也许操作系统很少看到故障，以至于 panic 是可以接受的。另一方面，使用普通磁盘的操作系统应该预期故障并更优雅地处理它们，这样一个文件中块丢失不会影响文件系统其余部分的使用。

xv6 要求文件系统适合一个磁盘设备，并且不改变大小。随着大型数据库和多媒体文件将存储需求推得越来越高，操作系统正在开发消除“一个文件系统对应一个磁盘”瓶颈的方法。基本方法是将许多磁盘组合成一个逻辑磁盘。RAID 等硬件解决方案仍然是最流行的，但当前趋势是尽可能在软件中实现这些逻辑。这些软件实现通常支持丰富的功能，例如通过添加或删除磁盘实时增长或缩小逻辑设备。当然，可以实时增长或缩小的存储层需要一个可以增长或缩小的文件系统：Unix 文件系统使用的固定大小 inode 块数组在这种环境中效果不佳。将磁盘管理从文件系统中分离出来可能是最干净的设计，但两者之间复杂的接口使一些系统（如 Sun 的 ZFS）将两者结合。

xv6 的文件系统还缺乏当今文件系统的许多其他特性；例如，它不支持快照和增量备份。

xv6 有两种不同的文件实现：管道和 inode。现代 Unix 系统有许多：管道、网络连接以及来自许多不同类型文件系统（包括网络文件系统）的 inode。与 fileread 和 filewrite 中的 if 语句不同，这些系统通常为每个打开的文件提供一个函数指针表，每个操作一个，并调用函数指针来调用该 inode 对该调用的实现。网络文件系统和用户级文件系统提供将那些调用转换为网络 RPC 并在返回前等待响应的函数。
