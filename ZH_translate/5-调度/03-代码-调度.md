# 代码：调度

> 来源：book-rev7.pdf，第 53–66 页（中文翻译）

上一节研究了 swtch 的低层细节；现在让我们把 swtch 当作已知，并考察从进程切换到调度器、再切回进程所涉及的约定。想要放弃 CPU 的进程必须获取进程表锁 ptable.lock，释放它持有的任何其他锁，更新自己的状态（proc->state），然后调用 sched。Yield (2522) 遵循此约定，sleep 和 exit 也是如此，我们稍后会看到。Sched 会再次检查这些条件 (2507-2512)，然后检查这些条件的一个推论：由于持有一把锁，CPU 应该在中断禁用的情况下运行。最后，sched 调用 swtch 将当前上下文保存在 proc->context 中，并切换到 cpu->scheduler 中的调度器上下文。

swtch 在调度器的栈上返回，仿佛调度器的 swtch 已经返回 (2478)。调度器继续 for 循环，找到要运行的进程，切换到它，然后循环重复。

我们刚才看到 xv6 在 swtch 调用期间持有 ptable.lock：swtch 的调用者必须已经持有该锁，并且锁的控制权传递给切换到的代码。这种约定在锁中不寻常；典型的约定是获取锁的线程负责释放锁，这样更容易推理正确性。对上下文切换来说，打破这种典型约定是必要的，因为 ptable.lock 保护进程状态与上下文字段的不变式，而这些字段在 swtch 执行期间不成立。如果 swtch 期间未持有 ptable.lock，可能出现的一个问题是：在 yield 将进程状态设置为 RUNNABLE 之后、但在 swtch 导致它停止使用自己的内核栈之前，另一个 CPU 可能决定运行该进程。结果是两个 CPU 在同一栈上运行，这是不对的。

内核线程总是在 sched 中放弃其处理器，并且总是切换到调度器中的同一位置，调度器（几乎）总是切换到 sched 中的进程。因此，如果打印 xv6 切换线程的行号，会看到以下简单模式：2478、2516、2478、2516，等等。这种两个线程之间的固定切换发生的函数有时被称为协程（coroutines）；在此示例中，sched 和 scheduler 是彼此的协程。

有一个情况是调度器 swtch 到新进程后不会最终到达 sched。我们在第 2 章见过这种情况：新进程首次被调度时，从 forkret (2533) 开始。forkret 之所以存在，只是为了遵守这个约定而释放 ptable.lock；否则新进程可以从 trapret 开始。

Scheduler (2458) 运行一个简单的循环：找到一个进程运行，运行到停止，重复。scheduler 在大部分动作中持有 ptable.lock，但每次外层循环迭代一次都会释放该锁（并显式启用中断）。这对于该 CPU 空闲（找不到 RUNNABLE 进程）的特殊情况很重要。如果空闲的调度器循环持续持有该锁，那么运行进程的其他 CPU 就永远无法执行上下文切换或任何与进程相关的系统调用，尤其永远无法将进程标记为 RUNNABLE，从而无法使空闲的 CPU 脱离其调度循环。在空闲 CPU 上定期启用中断的原因是：可能没有 RUNNABLE 进程，因为进程（如外壳）正在等待 I/O；如果调度器一直保持禁用中断，I/O 永远不会到达。

调度器循环遍历进程表，寻找可运行的进程，即 p->state == RUNNABLE 的进程。一旦找到进程，它设置每 CPU 的当前进程变量 proc，用 switchuvm 切换到进程的页表，将进程标记为 RUNNING，然后调用 swtch 开始运行它 (2472-2478)。

思考调度代码结构的一种方式是：它安排对每个进程强制一组不变式，并在这些不变式不成立时持有 ptable.lock。一个不变式是：如果进程是 RUNNING，必须设置好一切，使定时器中断的 yield 能正确地从进程切换离开；这意味着 CPU 寄存器必须保存进程的寄存器值（即它们不在 context 中），%cr3 必须指向进程的页表，%esp 必须指向进程的内核栈（这样 swtch 才能正确地压入寄存器），并且 proc 必须指向进程的 proc[] 槽。另一个不变式是：如果进程是 RUNNABLE，必须设置好，使空闲 CPU 的调度器可以运行它；这意味着 p->context 必须保存进程内核线程的变量，没有 CPU 在进程的内核栈上执行，没有 CPU 的 %cr3 指向进程的页表，也没有 CPU 的 proc 指向该进程。

维持上述不变式是 xv6 在一个线程中获取 ptable.lock（通常在 yield 中）并在另一个线程中释放锁（调度器线程或另一个内核线程）的原因。一旦代码开始修改运行进程的状态使其变成 RUNNABLE，就必须持有锁直到它完成恢复不变式：最早的释放点是调度器停止使用进程的页表并清除 proc 之后。同样，一旦调度器开始将可运行进程转换为 RUNNING，在完全完成之后（swtch 之后，例如在 yield 中）才能释放锁。

ptable.lock 还保护其他内容：进程 ID 的分配和空闲进程表槽位、exit 与 wait 的相互作用、避免丢失唤醒的机制（见下一节），可能还有其它。思考一下是否值得拆分 ptable.lock 的不同功能，当然是为了清晰，也许也是为了性能。
