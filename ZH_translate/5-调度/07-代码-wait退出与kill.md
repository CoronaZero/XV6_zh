# 代码：wait、exit 与 kill

> 来源：book-rev7.pdf，第 53–66 页（中文翻译）

sleep 和 wakeup 可用于许多涉及“需要等待可检查条件”的情况。正如我们在第 0 章看到的，父进程可以调用 wait 等待子进程退出。在 xv6 中，当子进程退出时，它不会立即死亡。相反，它切换到 ZOMBIE 进程状态，直到父进程调用 wait 得知退出。然后父进程负责释放与该进程相关的内存，并准备复用 struct proc。

每个进程结构在其 p->parent 中保留指向父进程的指针。如果父进程在子进程之前退出，初始进程 init 收养该子进程并等待它。这一步是必要的，以确保某个进程在子进程退出时清理它。所有进程结构都由 ptable.lock 保护。

wait 首先获取 ptable.lock。然后扫描进程表寻找子进程。如果 wait 发现当前进程有子进程，但没有一个退出，它会调用 sleep 等待某个子进程退出 (2439) 并循环。这里，sleep 中释放的锁是 ptable.lock，即我们上面看到的特殊情况。

exit 获取 ptable.lock，然后唤醒当前进程的父进程 (2376)。这可能看起来为时过早，因为 exit 还没有将当前进程标记为 ZOMBIE，但这是安全的：尽管父进程现在被标记为 RUNNABLE，但 wait 中的循环直到 exit 调用 sched 进入调度器释放 ptable.lock 之后才能运行，因此 wait 在状态被设置为 ZOMBIE (2388) 之前无法查看正在退出的进程。在 exit 重新调度之前，它会把正在退出进程的所有子进程重新交给 initproc (2378-2385)。最后，exit 调用 sched 放弃 CPU。

现在调度器可以选择运行正在退出进程的父进程，它正睡眠在 wait (2439) 中。sleep 的调用返回时持有 ptable.lock；wait 重新扫描进程表，找到状态为 ZOMBIE 的已退出子进程 (2382)。它记录子进程的 pid，然后清理 struct proc，释放与该进程相关的内存 (2418-2426)。

子进程本可以在 exit 期间完成大部分清理，但重要的是由父进程来释放 p->kstack 和 p->pgdir：当子进程运行 exit 时，它的栈位于分配为 p->kstack 的内存中，并且它使用自己的页表。只有在子进程最后一次通过调用 swtch（通过 sched）停止运行之后，它们才能被释放。这是调度器在自己的栈上运行而不是在调用 sched 的线程栈上运行的原因之一。

exit 允许应用程序终止自己；kill (2625) 允许应用程序终止另一个进程。实现 kill 有两个挑战：1）被杀进程可能正在另一个处理器上运行，在 xv6 终止它之前，它必须从其栈切换到其处理器的调度器；2）被杀进程可能处于睡眠状态，持有内核资源。为了应对这些挑战，kill 做得很少：它遍历进程表，为被杀进程设置 p->killed，如果该进程在睡眠，则唤醒它。如果被杀进程正在另一个处理器上运行，它很快会进入内核：要么因为它调用系统调用，要么因为发生中断（例如定时器中断）。当被杀进程再次离开内核时，trap 检查 p->killed 是否已设置，然后该进程调用 exit 终止自身。

如果被杀进程正在睡眠，调用 wakeup 会使被杀进程运行并从 sleep 返回。这可能很危险，因为进程从 sleep 返回，即使它等待的条件可能不为真。Xv6 仔细地编码，在每个 sleep 调用周围使用 while 循环，并在该 while 循环中检查 p->killed 是否已设置，如果是则返回其调用者。调用者还必须检查 p->killed 是否已设置，如果设置了则返回其调用者，依此类推。最终进程展开其栈到 trap，trap 将检查 p->killed。如果已设置，进程调用 exit 终止自身。我们在管道实现中看到在 sleep 周围的 while 循环中检查 p->killed 的例子 (6087)。

有一个 while 循环不检查 p->killed。IDE 驱动 (3979) 立即再次调用 sleep。原因在于它保证会被唤醒，因为它在等待磁盘中断。而且，如果它不等待磁盘中断，xv6 可能会困惑。如果在未发生中断前第二个进程调用 iderw，ideintr 将唤醒第二个进程，而不是最初等待中断的进程。第二个进程会认为它收到了等待的数据，但实际上它收到的是第一个进程读取的数据！
