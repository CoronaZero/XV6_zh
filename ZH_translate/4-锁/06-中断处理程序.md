# 中断处理程序

xv6 使用锁保护一个 CPU 上运行的中断处理程序免受另一个 CPU 上访问同一数据的非中断代码的干扰。例如，定时器中断处理程序 (3114) 递增 ticks，但另一个 CPU 可能同时正在 sys_sleep 中使用该变量 (3473)。锁 tickslock 同步两个 CPU 对单个变量的访问。

中断甚至可以在单个处理器上引起并发：如果中断被启用，内核代码可以在任何时刻停止，转去运行中断处理程序。假设 iderw 持有 idelock，然后被中断去运行 ideintr。ideintr 会试图获取 idelock，发现它已被持有，便等待它被释放。在这种情况下，idelock 永远不会被释放——只有 iderw 能释放它，而 iderw 在 ideintr 返回之前不会继续运行——因此该处理器乃至整个系统最终都会死锁。

为了避免这种情况，如果锁被中断处理程序使用，处理器决不能在中断启用时持有该锁。xv6 更保守：它绝不在中断启用时持有任何锁。它使用 pushcli (1555) 和 popcli (1566) 管理一个“禁用中断”操作的栈（cli 是禁用中断的 x86 指令）。acquire 在尝试获取锁之前调用 pushcli (1476)，release 在释放锁之后调用 popcli (1521)。Pushcli (1555) 和 popcli (1566) 不仅仅是 cli 和 sti 的封装：它们是有计数的，需要两次 popcli 调用才能撤销两次 pushcli 调用；这样，如果代码获取两把不同的锁，在两者都被释放之前中断不会重新启用。

重要的是，acquire 必须在可能获取锁的 xchg 之前调用 pushcli (1483)。如果顺序颠倒，在中断启用状态下持有锁的那几个指令周期就会产生死锁，而不巧的定时中断会使系统死锁。同样重要的是，release 必须在释放锁的 xchg 之后才调用 popcli (1483)。

中断处理程序与非中断代码之间的交互提供了一个很好的例子，说明可重入锁为什么有问题。如果 xv6 使用递归锁（如果第一次 acquire 发生在同一 CPU 上，则允许在该 CPU 上第二次 acquire），那么中断处理程序就可以在非中断代码处于临界区时运行。这可能会造成破坏，因为当中断处理程序运行时，处理器依赖的不变式可能暂时被违反。例如，ideintr (3902) 假设具有未完成请求的链表是良构的。如果 xv6 使用递归锁，则 ideintr 可能在 iderw 操纵链表的中途运行，链表最终会处于错误状态。
